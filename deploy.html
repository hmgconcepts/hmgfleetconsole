🚀 Deployment RunbookEvery step, every click, every gotcha — from ZIP to fully-armed fleet monitoring, no assistance needed

What you are deploying: a folder of static files (HTML/CSS/JS). No build step, no npm, no server, no environment variables, no database of its own. Any static host serves it; we use GitHub (storage + the keep-alive robot) and Vercel (hosting) because both are free and you already use them for clients.

Time: ~20 minutes for Phases 1–3 · ~2 minutes per client project in Phase 4 · Phase 5 is optional hardening. Cost: ₦0.

Phase 0 — What you need before starting

  • ✅ A GitHub account (github.com — free). You already have hmgconcepts.
  • ✅ A Vercel account (vercel.com — free "Hobby" plan), signed in with GitHub so imports are one click.
  • ✅ The hmg-fleet-console.zip file, unzipped into a folder on your computer. Confirm the folder contains: index.html, login.html, projects.html, incidents.html, reports.html, board.html, tools.html, guide.html, deploy.html, about.html, settings.html, sw.js, manifest.json, README.md, an assets folder, a tools folder, and a (possibly hidden) .github folder.
  • ✅ ~20 minutes and a modern browser (Chrome or Edge recommended).
💡 Dot-folders are hidden by default. On Windows: File Explorer → View → tick "Hidden items". On Mac: press Cmd+Shift+. in Finder. You need to SEE the .github folder for step 1.3's check.

Phase 1 — Put the console online (GitHub + Vercel)

1
Create the GitHub repository. Open github.com/new. Fill exactly:
  • Owner: your account (e.g. hmgconcepts)
  • Repository name: hmg-fleet-console
  • Visibility: Private ← important. This is an internal ops tool; a private repo also protects the login-hash file.
  • Do NOT tick "Add a README" or any other initializer — the ZIP already contains everything.
Click Create repository. You land on an empty-repo page — keep it open.
2
Upload the files. On that empty-repo page click the link "uploading an existing file". Open your unzipped folder, select everything inside it (Ctrl+A / Cmd+A) and drag it onto the GitHub upload area. Wait for every file to list, write a commit message like initial console, click Commit changes.
⚠️ Known GitHub limitation: the drag-and-drop uploader silently SKIPS dot-folders, so .github/workflows/fleet-keepalive.yml (the keep-alive robot) will be missing. Step 3 fixes it in one minute. (If you instead push with git from a computer, dot-folders upload fine and step 3 is unnecessary.)
3
Add the workflow file by hand. In the repo: Add file → Create new file. In the name box type exactly: 
.github/workflows/fleet-keepalive.yml
(typing the / characters creates the folders). On your computer, open the same file from the ZIP in Notepad/TextEdit, copy ALL of it, paste into GitHub's editor, click Commit changes.
Verify: the repo's Actions tab now lists a workflow called "Fleet keep-alive". If yes — done.
4
Deploy on Vercel. Go to vercel.com → Add New… → Project. Find hmg-fleet-console in the repo list (if it is missing, click "Adjust GitHub App Permissions" and grant access to the repo) → Import. On the configure screen:
  • Framework Preset: Other
  • Root Directory: leave as ./
  • Build Command / Output Directory / Install Command: leave empty / defaults — do not type anything
Click Deploy. ~30 seconds later you get your URL, e.g. https://hmg-fleet-console.vercel.app. Every future commit to the repo redeploys automatically.
Alternative hosts (equally fine, also free): GitHub Pages — repo → Settings → Pages → Source "Deploy from a branch" → main / root (note: on a private repo, Pages requires a paid plan — Vercel does not); Netlify — drag the folder onto app.netlify.com/drop. The console also runs from a local folder via file://, but login and PIN need HTTPS, so treat that as read-only preview.

Phase 2 — First login & change the password (DO NOT SKIP)

5
Sign in with the shipped defaults. Open your Vercel URL. You are redirected to the sign-in page. Enter: 
Username: hmgadmin
Password: ChangeMe#2026
Tick "Keep me signed in" on your own machines. You land on the Dashboard.
6
Generate YOUR credentials. Go to ⚙️ Settings → 🔑 Login credentials. Type your new username and a STRONG password (12+ characters, mix words/digits/symbols, not reused anywhere). Click ⚙️ Generate file text → 📋 Copy file text. The password itself never appears in the generated text — only its salted SHA-256 hash.
7
Commit the new credentials. GitHub → your repo → open assets/js/auth-config.js → click the ✏️ pencil → select ALL existing content → paste the generated text over it → Commit changes. Vercel redeploys in ~1 minute.
Verify safely: open a private/incognito window → your URL → sign in with the NEW credentials. Only after that succeeds, close the incognito window. (Your existing session keeps working through the change, so a typo can never lock you out while you still have a signed-in tab.)
8
Optional: session PIN. Settings → 🔐 Console PIN — an extra once-per-session lock for shared machines. Independent of the login.

Phase 3 — Install it as an app on your devices

9

The console becomes a desktop app: own window, own icon, instant offline-shell startup, and app shortcuts on right-click (Keep ALL alive · Wallboard · Incidents).
10
Your Android phone: open the URL in Chrome → the same banner appears → Install. iPhone/iPad: open in Safari → Share ⬆ → Add to Home Screen → Add (the banner shows these exact steps on iOS automatically).
11
The office wallboard TV (optional but excellent): on the TV's browser (or a stick PC), sign in → install → open 🖥️ Wallboard → ⛶ Fullscreen. It re-checks the fleet automatically (default every 10 min). Green room = calm room.

Phase 4 — Register the fleet

12
Collect each project's two values. Every registration needs only the Supabase URL and the anon key:
  • HMG product sites (School Connect / Tutoring Connect / DramaConnect / HMG CBT): open the client site's config in any browser — e.g. https://gosaportal.vercel.app/assets/js/config.js — and copy the values of SUPABASE_URL and SUPABASE_ANON_KEY.
  • Any other Supabase project: its Supabase dashboard → Project Settings → API → "Project URL" + "anon public" key.
⚠️ NEVER copy the service_role key — into this console or any frontend, ever. The console detects and refuses it; the 🔍 key inspector (Ops Toolkit) tells you what any key is before you use it.
13
Register each project. 🗂️ Projects → fill Name, URL, anon key → choose the Type (this decides whether the subscription verdict is probed) → add the live site URL (enables the site-reachability probe) → optionally tags, environment, client contact, renewal date, fee note → ➕ Add & test. Within seconds the row shows a health score and a green keep-alive pill.
Reading the first result: ✓ pinged just now = perfect · RPC missing = non-HMG project needing step 14 · unreachable = wrong URL, or the project is already paused (restore it in the Supabase dashboard first, then ⚡).
14
Non-HMG projects only: add the keep-alive endpoint. 🧰 Ops Toolkit → "Keep-alive SQL" → 📋 Copy → that project's Supabase dashboard → SQL Editor → New query → paste → Run ("Success. No rows returned" is correct) → back in the console press that row's ⚡ — it turns green. The snippet is idempotent (safe to run twice) and touches nothing but its own heartbeat table.
15
Switch on the automation + first backup. Dashboard → tick 🤖 Auto-pilot. Settings → tick 🔔 Desktop notifications (allow the browser prompt). Ops Toolkit → ⬇ Download full backup → save the JSON into your Google Drive. (The console reminds you if a backup ever gets 14+ days old.)

Phase 4b — ☁️ Cloud Sync (same fleet on your phone, laptop and the office PC)

15b
Create the vault (once for the whole company). Create ONE free Supabase project owned by HMG (name it e.g. hmg-fleet-vault) → SQL Editor → paste the vault SQL (Settings → ☁️ Cloud Sync → 📋 Copy vault SQL) → Run ("Success. No rows returned").
15c
Connect this device. Settings → ☁️ Cloud Sync → fill: vault project URL + anon key (its Project Settings → API), 🎲 generate a Vault ID, choose a STRONG passphrase (this is the encryption key — write it somewhere safe; it is never uploaded and cannot be recovered) → 💾 Save & test sync → expect "Cloud Sync is ON".
15d
Connect every other device. Sign in to the console on the phone/laptop → Settings → ☁️ Cloud Sync → enter the SAME four values → Save & test. Within seconds the full fleet, incident journal and history appear. From then on everything stays in step automatically (pull on open, push on change). All data in the vault is end-to-end encrypted — even HMG's own vault database only ever contains ciphertext.

Phase 5 — Hands-off keep-alive layers (closed-tab protection)

Do at least ONE. Doing all three = triple redundancy on top of the console itself; each alone prevents the 7-day pause.

16
Layer A — GitHub Actions (recommended first; already in your repo).
  1. 🧰 Ops Toolkit → "GitHub Actions FLEET_TARGETS secret" → 📋 Copy secret value (one keep-alive URL per line, auto-built from your registered fleet).
  2. GitHub repo → Settings → Secrets and variables → Actions → New repository secret → Name: FLEET_TARGETS → paste → Add secret.
  3. Test now: repo → Actions tab → "Fleet keep-alive" → Run workflow → wait ~30 s → open the run → every project should print OK <host> (200).
It then runs every 2 days forever. When the fleet changes, regenerate in the Toolkit and edit the secret — no code edit. A failing project makes the run red and GitHub emails you automatically: a free alarm channel.
17
Layer B — cron-job.org. Free account → Create cronjob → Title: the project name → URL: that row's 📋 keep-alive URL → Advanced: request method POST → schedule: every 3 days → Save → "Run now" to test (expect HTTP 200). Repeat per project. Enable failure notifications in its settings — second free alarm channel.
18
Layer C — UptimeRobot. Free account → Add New Monitor → type HTTP(s) → URL: the keep-alive URL and/or the client's live site → interval 5 minutes → alert contact: your email. External vantage point (distinguishes "their ISP" from "the project is down") + third free alarm channel + optional public status pages per client.

Phase 6 — Daily, weekly & monthly operations

19
Daily (5 seconds): glance at the Dashboard or the Wallboard. "✅ All clear" → done. Anything listed → its fix button is beside it (⚡ / 🩺 / 💬 / resume / renewal follow-up).
20
When a client pays or renews: Projects → ✏️ that row → update the renewal date (and fee note) → 💾 Save. Log it in 🚨 Incidents as a manual ℹ️ entry ("Renewal collected — 2 terms") so the money trail lives in the journal. If it is a School Connect subscription renewal, also issue their activation key (tools/make-license-key.mjs in the School Connect repo) — the verdict pill flips to ✓ on the next check.
21
New client goes live: register (step 13) → Ops Toolkit → refresh Layer A's secret and/or add a Layer B/C job → new backup. Two minutes, fully protected.
22
Monthly (10 minutes): 📈 Reports → 🖨️ Print/PDF for the ops record · 🚨 Incidents → export CSV → archive · 🧰 Ops Toolkit → fresh backup JSON to Drive · glance at the renewal calendar for the month ahead.

Updating the console later

  1. Edit files (GitHub web editor or locally + git push). Vercel redeploys automatically.
  2. If you changed any HTML/CSS/JS: bump the version constant at the top of sw.js (e.g. hmg-fleet-v1.1-…-2 → -3) so every installed copy refreshes its offline cache on next load.
  3. Exception you never worry about: auth-config.js is fetched network-first, so login changes take effect on the next online load even without a version bump.
  4. Your fleet data is never touched by updates — it lives in each browser, not in the repo.

Stronger login alternatives (optional, still free)

The built-in login (salted-hash file + throttled attempts) keeps out anyone who stumbles on the URL. If you want server-enforced authentication in front of it — nothing loads at all without passing a real identity provider — the free-tier expert option is:

Cloudflare Access (Zero Trust — free for up to 50 users):

  1. Add a domain you control to Cloudflare (free plan), e.g. fleet.hmgconcepts.com, and point it at the Vercel deployment (Vercel → project → Settings → Domains → add the same hostname; set the CNAME Cloudflare shows).
  2. Cloudflare dashboard → Zero Trust → Access → Applications → Add application → Self-hosted → application domain = your hostname.
  3. Add a policy: Allow → Emails → your email address(es). Choose "One-time PIN" as the login method (no extra accounts needed).
  4. Now every visit must pass Cloudflare's checkpoint (email OTP) BEFORE a single byte of the console is served. The built-in login remains as a second layer.

Also worth knowing: Vercel's own password protection is the simplest possible option but sits on a paid tier — Cloudflare Access is the free equivalent and stronger. And regardless of any gate, the fail-safe stands: the console holds only public anon keys; client business data is sealed by RLS on the client's own database.
