🚀 DeploymentClear, unambiguous, step-by-step — from ZIP to fully-armed fleet monitoring

Total time: ~15 minutes for Phases 1–2, plus ~2 minutes per client project. Everything uses free tiers only. The console is pure static files — no build step, no npm, no server, no environment variables.

Phase 1 — Put the console online (GitHub + Vercel)

1
Create the GitHub repository. Go to github.com/new → Owner: your account (e.g. hmgconcepts) → Repository name: hmg-fleet-console → visibility Private (recommended: this is an internal ops tool; the pages also carry noindex either way) → Create repository. Do NOT add a README/.gitignore from the wizard — the ZIP already has everything.
2
Upload the files. Unzip hmg-fleet-console.zip on your computer. On the new repo page click uploading an existing file, drag in EVERYTHING from inside the unzipped folder (including the assets folder). Important: the GitHub drag-and-drop uploader skips dot-folders, so after the first commit add the workflow by hand: repo → Add file → Create new file → name it exactly .github/workflows/fleet-keepalive.yml → paste the contents of that file from the ZIP → Commit. (If you use git push from a computer instead, the dot-folder uploads automatically and this extra step disappears.)
3
Deploy on Vercel. vercel.com → Add New… → Project → Import the hmg-fleet-console repo → Framework preset: Other → leave Build Command and Output Directory empty (static site) → Deploy. You get https://hmg-fleet-console.vercel.app (or similar). Every future git push auto-redeploys.
Alternative hosts, equally fine: GitHub Pages (repo → Settings → Pages → Deploy from branch → main / root) or Netlify drag-and-drop. The console also runs directly from a local folder via file:// — only the PIN feature needs HTTPS.
4
Open it & install as an app (optional). Visit the URL, confirm the dashboard loads. In Chrome/Edge use the address-bar install icon ("Install HMG Fleet Console") — it becomes a desktop/mobile app with offline shell.
5
Set a console PIN (optional, for shared machines). Settings → Console PIN → enter a PIN → Save. Asked once per browser session.

Phase 2 — Register the fleet

6
Collect each project's URL + anon key. For HMG product sites (School Connect, Tutoring Connect, DramaConnect, HMG CBT): open the client site's assets/js/config.js in the browser (e.g. https://gosaportal.vercel.app/assets/js/config.js) and copy SUPABASE_URL and SUPABASE_ANON_KEY. For any other project: Supabase dashboard → Project Settings → API → Project URL + anon public key. Never the service_role key — the console refuses it anyway.
7
Register each project. Projects page → fill Name, URL, anon key, Type, live site URL → add tags, client contact, renewal date, fee note as desired → ➕ Add & test. The console immediately health-checks and pings it. A RPC missing keep-alive result on a non-HMG project means: run the Ops Toolkit SQL once (next step).
8
Non-HMG projects only: add the keep-alive RPC. Ops Toolkit → "Keep-alive SQL" → 📋 Copy → that project's Supabase dashboard → SQL Editor → paste → Run. Back in the console press that row's ⚡ — it should turn green. (HMG product schemas already ship sc_keep_alive; skip this.)
9
Turn on Auto-pilot & take a backup. Dashboard → tick 🤖 Auto-pilot. Then Ops Toolkit → ⬇ Download full backup and drop the JSON in your Google Drive. (The console reminds you if a backup is ever 14+ days stale.)

Phase 3 — Hands-off keep-alive layers (tab closed, everything still protected)

Do at least ONE of these; doing all three gives triple redundancy. Each alone is sufficient to prevent the 7-day pause.

10
Layer A — GitHub Actions (recommended first; ships in this repo). Ops Toolkit → cron pack → copy the FLEET_TARGETS secret value (one keep-alive URL per line). Then GitHub repo → Settings → Secrets and variables → Actions → New repository secret → Name: FLEET_TARGETS → paste → Add secret. Test it: repo → Actions → "Fleet keep-alive" → Run workflow → confirm every line prints OK. It then runs every 2 days forever; when the fleet changes, just edit the secret (Ops Toolkit regenerates the list).
11
Layer B — cron-job.org. Free account at cron-job.org → Create cronjob → URL: a project's 📋 keep-alive URL → Request method: POST → Schedule: every 3 days → Save. Repeat per project (Ops Toolkit lists all URLs). Its dashboard also emails you on failures — a free extra alarm.
12
Layer C — UptimeRobot. Free account at uptimerobot.com → Add monitor → HTTP(s) → URL: the same keep-alive URL (GET pings still count as project activity) and/or the client's live site URL → interval 5 minutes. This adds an external vantage point + email alerts + public status pages if you ever want one per client.

Phase 4 — Daily operations

13
Morning glance. Open the dashboard (or keep the Wallboard on a spare screen). "Needs attention" empty = done in 5 seconds. Anything listed has its fix button right there.
14
When a client pays / renews. Projects → ✏️ edit → update the renewal date → Save. Log it in Incidents ("manual entry") so the money trail is in the journal too.
15
New client goes live. Register (step 7) → add their URL to the FLEET_TARGETS secret and/or cron-job.org (Ops Toolkit regenerates both lists) → fresh backup. Two minutes, fully protected.
16
Monthly. Reports page → 🖨️ Print/Save as PDF for the ops record; Incidents → export CSV if you want the journal archived; Ops Toolkit → fresh backup JSON to Drive.

Updating the console later

Edit files → git push (or upload via GitHub web) → Vercel redeploys automatically. If you change any HTML/CSS/JS, bump the version string const CACHE = 'hmg-fleet-v…' at the top of sw.js so every installed copy refreshes its offline cache on next load. Your data is untouched by updates — it lives in the browser, not the repo.

Troubleshooting

  • "RPC missing" on keep-alive → the project lacks sc_keep_alive. Run the Ops Toolkit SQL once in its Supabase SQL Editor.
  • Everything shows "unreachable" → check your own internet first; then the Supabase status page. A paused project also answers nothing — restore it from the Supabase dashboard, then ping immediately.
  • Key rejected on registration → you pasted a service_role key (never do that), a key from a different project than the URL, or an expired key. The error message says which.
  • GitHub Action fails for one line → open the run log; the failing host is named. Usually the project was paused (restore it) or the URL line has a stray character.
  • Fleet list vanished → browser data was cleared or it's a different browser/profile. Ops Toolkit → Restore from your latest backup JSON. (This is why the console nags about backups.)
  • PIN forgotten → clear this site's data in the browser (fleet list goes too), reload, restore from backup, set a new PIN.
