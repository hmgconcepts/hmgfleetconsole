📖 Feature GuideThe complete manual — every page, every feature, every concept, explained for a first-time user

HMG Fleet Console is HMG CONCEPTS' internal operations platform: one place to watch, protect and manage every client project we build — School Connect schools, Tutoring Connect practices, DramaConnect departments, HMG CBT deployments, and any other Supabase-backed project. It is 100% free-tier: no server of its own, no database of its own, no paid API, no AI API. Everything runs in your browser plus three optional free external services (GitHub Actions, cron-job.org, UptimeRobot).

🧭 The mission this console serves: "Recurring payments should not keep your schools from having online presences." Free Supabase projects are paused after 7 days without database activity. The console's single most important job is to make sure that never happens to any client — even one whose subscription with HMG has expired. Their data stays alive untouched; they renew whenever they are ready; nothing is ever lost.

💡 Tip: the 🤖 Fleet Bot (bottom-right of every page) answers questions about any page or feature — and live questions about your fleet like "status" or "who is at risk?".

0 · A 5-minute mental model (start here)

Think of the console as an air-traffic control tower for HMG client projects:

  • Each client project (a school's School Connect, a church's DramaConnect…) is a plane: its own Supabase database + its own Vercel website, owned by the client.
  • The tower's radar = health checks (is the database answering? auth? storage? the website? how fast?).
  • The tower's most important duty = keep-alive: free Supabase "planes" fall asleep after 7 days without activity; the console keeps every one awake with a tiny database write.
  • The flight log = the incident journal: every problem and recovery, recorded automatically with timestamps.
  • The billing desk = renewal watch: who has paid, who is due, who is overdue — with their phone number one click away.

Daily routine for a first-time operator: open the Dashboard → if "Needs attention" says ✅ All clear, you are done (5 seconds). If not, every alert has its fix button right beside it. Everything else in this guide is depth, not obligation.

Register and maintain every monitored project. "➕ Add & test" checks and pings the project immediately so mis-wiring is caught in seconds. 2 · Keep-alive engine (the reason this console exists)

2.1 What a "ping" actually does

Every ping calls the project's public sc_keep_alive RPC, which performs a real database write — it updates a single heartbeat row (timestamp, source label, counter). A write is the gold-standard activity signal, far stronger than loading a web page. The RPC is SECURITY DEFINER and the heartbeat table itself is sealed by RLS: the anon key can bump the heartbeat and do absolutely nothing else.

2.2 The traffic light

Each project's keep-alive cell is coloured by heartbeat age: ✓ fresh → ⚠ older than the warning threshold (default 3 days) — "ping soon" → 🚨 older than the alarm threshold (default 6 days) — PAUSE RISK. Both thresholds are Settings-adjustable and the alarm is deliberately kept below Supabase's 7-day line so you always have at least a one-day buffer.

2.3 The four independent layers

  1. Console layer: ⚡ buttons, fleet-wide "Keep ALL alive", 🤖 auto-pilot on a timer, and the stale-heartbeat wake-up — the moment any console page opens, anything unpinged for 5+ days is pinged automatically and silently.
  2. GitHub Actions layer: the repo ships .github/workflows/fleet-keepalive.yml. One repository secret (FLEET_TARGETS, one keep-alive URL per line — the Ops Toolkit generates it) and GitHub's own servers ping the entire fleet every 2 days, forever, free, with per-project OK/FAIL lines in the run log and a red run (plus GitHub's automatic email) if anything fails.
  3. cron-job.org layer: free scheduled POSTs to each project's 📋 keep-alive URL every 3 days, with failure emails.
  4. UptimeRobot layer: free 5-minute monitors on the same URLs and/or the live sites — the pings double as activity AND give an external vantage point + public status pages if wanted.
Any ONE layer alone prevents a pause. Four exist so that no single failure — a closed tab, a disabled workflow, a forgotten cron account — can ever cascade into a paused client.

2.4 ⏸️ Monitoring pause

For planned downtime (school on a long break, migration in progress) pause a project: auto-pilot, fleet actions and alerts skip it; registration, notes, history and incidents are kept; one click resumes. This replaces the bad old choice between "delete it" and "let it spam alerts".

3 · Health monitoring & the score

3.1 The five probes (per project, per check)

  1. REST / database API + latency — is PostgREST answering and how fast? Important nuance: a 401/404 on the bare REST root still counts as ALIVE, because newer Supabase stacks answer 401 there by design; only a network failure or 5xx marks it down. (This prevents false alarms — verified against live HMG projects.)
  2. Auth service — GoTrue's health endpoint. If this is down, nobody can sign in even though the site loads; probing it separately points you straight at the culprit.
  3. Storage service — the storage status endpoint (uploads, report attachments, gallery images).
  4. Heartbeat age — freshness of the keep-alive write (§2).
  5. Live site — optional site URL fetched in no-cors mode; even an opaque response proves DNS + TLS + a listening server (i.e. the Vercel deployment exists and responds).

Plus, for HMG product projects, the subscription verdict (§4). Every check also stores a history sample powering sparklines and uptime % (§7).

3.2 The health score, fully disclosed

Start at 100, subtract: −45 database API down · −20 Auth down · −10 site down · −5 Storage down · −10 heartbeat past warning / −25 past alarm · −10 subscription expired/suspended · −5 latency over 2.5 s · −5 heartbeat unknown. Clamp to 0–100. Bands: 85–100 healthy 60–84 degraded < 60 critical. The weighting mirrors real impact — a dead database dwarfs everything else. Deterministic: same inputs, same score, no black box.

4 · Subscription watch & the pause-proof guarantee

4.1 How the console sees a client's subscription

Every HMG product ships a public sc_license_status RPC whose verdict is computed server-side (the client's clock or edits cannot fake it): ✓ active / lifetime · ⚠ warning / grace · 🔒 expired / suspended. The console calls it on every health check and shows the verdict per project; a verdict change is logged as an incident, so "when did this school expire?" always has an answer.

4.2 What happens when a School Connect client does NOT pay one-time

Subscription clients are built with the generator's subscription license model: the site carries a signed license (status, expiry, grace days). Enforcement is server-computed and tamper-evident — expiry shows a renewal banner during grace, then a full lock screen with the renewal contact. Renewal is a signed activation key generated at HMG (tools/make-license-key.mjs), pasted by the school on their license page: single-use, cryptographically signed with the site's secret salt, impossible to forge or reuse. No database access needed at renewal time — and the same tool can issue a lifetime key the day a client completes a one-time purchase.

4.3 The pause-proof guarantee (the part clients love)

An expired subscription never endangers a school's data. Three mechanisms make this true:
1 · Keep-alive is license-independent — every layer in §2.3 keeps pinging an expired project.
2 · The client's own locked portal page pings the heartbeat too (src: locked-portal) — even a school that only ever looks at its lock screen stays awake.
3 · This console watches the verdict fleet-wide, so HMG follows up with the right school at the right time.
Result: the school renews when ready, HMG applies the activation key, and everything is exactly as they left it. "Recurring payments should not keep your schools from having online presences."

5 · Incident journal

5.1 Automatic incidents (state transitions, logged exactly once)

Health checks compare each result with the previous one and log only changes: API down↔up · Auth down↔up · site down↔up · heartbeat crossing into pause-risk · subscription verdict change · keep-alive failure (HTTP error / unreachable / missing RPC) · project registered/removed · monitoring paused/resumed. Recoveries are logged pre-resolved. No duplicate spam: a project that stays down does not re-log every check.

5.2 Severities

🚨 critical outage-class events · ⚠️ warning degradations and license changes · ✅ good recoveries · ℹ️ info registrations and routine notes. Critical unresolved entries surface on the Dashboard until resolved.

5.3 The manual diary — why it matters

Log renewals collected, SQL packs applied, client conversations, deploys, maintenance windows. Six months later, "what happened with this school in March?" is a two-second filter instead of an archaeology dig through chats. Export the whole journal to CSV any time.

6 · Business layer (clients, renewals, tags)

  • Client contact card — name, phone/WhatsApp, email per project. Alerts that need a human show the number right there; the 💬 button opens WhatsApp with a prefilled situation report (§12).
  • 📅 Renewal watch — renewal/next-payment date + fee note per project. Dashboard warns inside the warning window (default 14 days, configurable) and flags overdue; Reports renders the full calendar soonest-first. This is the collections workflow, built in.
  • Tags & environments — free-form tags (lagos, priority, church…) and a production/staging/demo badge, all searchable, so "every priority school in Lagos" is one keystroke.

7 · Reports, uptime & wallboard

Sampling model: every health check (manual, auto-pilot, wallboard refresh or page-open wake-up) stores one sample per project — latency, up/down, score — capped at 96 samples locally. From these the console computes per-project uptime % and average latency, latency sparklines, and a fleet-average roll-up. This is the internal, zero-dependency layer; for audit-grade, 5-minute-resolution external history, pair each site with a free UptimeRobot monitor. The Reports page prints to PDF; the Wallboard displays the same truth as traffic lights for the room.

8 · Ops Toolkit, tool by tool

  • 🔧 Keep-alive SQL — one idempotent paste (a heartbeat table + a SECURITY DEFINER RPC) makes ANY non-HMG Supabase project monitorable. RLS on real tables untouched. HMG products already ship the RPC.
  • ⏰ Cron pack generator — regenerates, from the live fleet list, both the cron-job.org/UptimeRobot URL list and the exact FLEET_TARGETS secret value. Fleet changed? Open Toolkit → copy → paste. Done.
  • 🔍 Anon key inspector — decodes any Supabase JWT locally (nothing is sent anywhere): role (service_role flagged in red — and registration outright refuses one), owning project ref (catches key/URL mix-ups), expiry date.
  • 💾 Backup center — §13.
  • 🧪 Quick probe — REST/Auth/Storage/keep-alive presence for any URL+key in ~2 seconds, no registration needed. Perfect for "is it them or is it me?" moments.

9 · Login, sessions & access control

9.1 How sign-in works

Random visitors — even with the live URL — see only the login page; every console page verifies the session before rendering anything. Credentials live in one file: assets/js/auth-config.js. It stores the username and a salted SHA-256 hash of the password (never the password). Sessions are self-expiring tokens (default 12 h; "Keep me signed in" persists across restarts). Wrong-password throttling: 5 attempts → 15-minute lockout.

🚨 The red security banner (V1.5): while the console detects the shipped default password still in force, EVERY page shows an unmissable red banner (and Self-Test shows a red row). It disappears the moment your own credentials are committed. This was added after a live audit found a deployment running the defaults with a public repo — the two-minute fix is below.

9.2 Changing the login (2 minutes, no tools)

  1. Settings → 🔑 Login credentials → type new username + password → Generate file text.
  2. GitHub → assets/js/auth-config.js → ✏️ Edit → select-all → paste → Commit.
  3. Vercel redeploys (~1 min). Test in an incognito window before closing your signed-in session.

9.3 Honest scope + the stronger free option

This is a strong gate for a static site: it fully blocks casual visitors and resists brute force (salted hash + throttle + strong password). It is not a server — a determined attacker who obtains the repo file could try passwords offline, which is why the repo stays private and the password strong. The real safety net is unchanged either way: the console holds only public anon keys, and client RLS seals all business data. Want bank-grade? Put the Vercel deployment behind Cloudflare Access (free ≤ 50 users) — the Deployment page has the walkthrough. Both can run together.

  • 📣 Webhook alerts (V1.3): critical incidents pushed to Discord / Slack / Telegram (or any webhook) in real time — free push to your phone with the console closed. Settings → Alerts, with a 🧪 test button.

  • 🧪 Self-Test page (V1.4): one-click diagnostics of every subsystem — environment, login (unchanged-default-password detector), fleet health, live connectivity, keep-alive layers, alert channels, Drive/Sync continuity, a real AES-GCM tamper-reject round-trip, and subscription-watch coverage — each result with its exact next step. Run after every deploy and on every new device.

13 · Data, backups, portability & ☁️ Cloud Sync

🟢 Google Drive backup (V1.3) — no extra Supabase needed. Settings → Google Drive backup → Connect (one popup per device). From then on every fleet change auto-backs-up (~20 s debounce) to a hidden app-data folder in YOUR OWN Google Drive — the scope is drive.appdata, so the console can never see your real Drive files, and the backups are invisible to other apps. New device: sign in → Connect → 📥 Restore → the newest backup merges into the device (union by project URL / incident id — never overwrites). Rotation keeps the newest 5 generations; an optional passphrase seals backups with AES-GCM-256 before upload. The OAuth Client ID ships in assets/js/gdrive-config.js — safe to commit because a web Client ID is public by design and Google enforces the Authorized JavaScript Origins list (only your deployed URL can use it); no client secret exists in this architecture at all.
☁️ Cloud Sync (V1.2) — the same fleet on every device. Signing in on a new phone or laptop used to start empty, because the console is local-first. Now: Settings → Cloud Sync → run the one-time vault SQL in a free HMG-owned Supabase project → fill vault URL + anon key + vault ID (🎲 generates one) + a strong passphrase → Save & test → repeat the same four values on every device. From then on, every device pulls on page open and pushes ~8 s after any change. Zero-knowledge: the fleet is encrypted in your browser with AES-GCM-256 (key derived from your passphrase, PBKDF2 · 210,000 iterations, fresh salt every write) — the vault stores only ciphertext, and a tampered blob fails authentication rather than injecting data. Merge, never overwrite: projects are united by URL (freshest status wins), incidents by id, history samples by timestamp — two devices working simultaneously both end up complete. Forgot the passphrase? The vault is unreadable by design; set a new passphrase and push again from any device that still has the fleet.

ALL console data lives in this browser's localStorage under four keys: projects, settings, incident journal, latency history. Nothing is ever sent to any server. Consequences and features:

  • Backup = one JSON file with all four sets (Ops Toolkit → Download). Keep it in Google Drive. The console nags if none was taken for 14+ days.
  • Restore anywhere in two clicks; dedupe is by Supabase URL so restoring twice never duplicates. Backups from the original single-file console restore unchanged (same key, auto-migrated with new fields defaulted).
  • CSV exports: fleet overview and incident journal for spreadsheets.
  • Multi-machine reality: each browser is its own copy. Pick ONE primary machine as the source of truth and move via backup/restore — or simply register the fleet on both and let each ping independently (double keep-alive coverage; histories will differ, which is fine).

14 · Security model — privacy by construction

  • The console stores only public anon keys. Client-side Row-Level Security means an anon key can bump a heartbeat and read the public license verdict — nothing else. Students, fees, results, members: unreadable by construction, not by promise.
  • The console never signs into client portals, never reads business tables, never requests a service_role key, and rejects one on paste (JWT role check).
  • No server, no analytics, no third-party scripts, no CDNs — pure static files; the whole attack surface is your browser and your GitHub repo.
  • Login gate (§9) + optional PIN + private repo + optional Cloudflare Access = layered access control, all free.

15 · Known limits (honest engineering)

  • Browser checks measure reachability from your network — your own ISP hiccup can look like a fleet outage. Cross-check with UptimeRobot before declaring one (the Quick Probe helps too).
  • Uptime % is sampled (≤ 96 samples/project), a trend indicator — UptimeRobot is the audit-grade record.
  • Auto-pilot needs an open tab; that is precisely why the three external layers exist.
  • localStorage is per-browser and cleared if the user clears site data — hence backups.
  • The static login is a gate, not a vault (§9.3); the data-security guarantee never depends on it.

16 · Glossary

  • Anon key — Supabase's public client key; safe to expose, powerless beyond what RLS allows.
  • Service_role key — Supabase's god-mode key. Never used here; refused on paste.
  • RLS — Row-Level Security; per-row database permissions enforced by PostgreSQL itself.
  • RPC — a database function callable over HTTP (e.g. sc_keep_alive, sc_license_status).
  • Heartbeat — the timestamp row that keep-alive writes; its age is the pause-risk measure.
  • Pause — Supabase freezing a free project after 7 inactive days (data kept, everything stops until manually restored).
  • Grace period — days after subscription expiry during which the client portal still works with a renewal banner.
  • Activation key — the signed, single-use code HMG issues on renewal or lifetime purchase.
  • PWA — Progressive Web App; installable website with offline shell and app icon.
  • NOC — Network Operations Center; the wallboard emulates one for ₦0.
