📖 Feature GuideWhat every feature does, why it exists, and how to use it

HMG Fleet Console is HMG Concepts' internal operations platform: one place to watch, protect and manage every client project we build — School Connect schools, Tutoring Connect practices, DramaConnect departments, HMG CBT deployments, and any other Supabase-backed project. It is 100% free-tier: no server, no database of its own, no paid API, no AI API. Everything below runs in your browser plus three optional free external services (cron-job.org, UptimeRobot, GitHub Actions).

🧭 Mission context: "Recurring payments should not keep your schools from having online presences." Free Supabase projects are paused after 7 days without database activity. The single most important job of this console is to make sure that never happens to any client — even one whose subscription with us has expired. Their data stays alive; they renew when they are ready.

1 · Keep-alive engine (the reason this console exists)

1.1 ⚡ Keep ALL alive now

One click performs a real database write in every registered project by calling its public sc_keep_alive RPC. A write is the gold standard of "activity" — far stronger than merely loading a page. Each ping updates a single heartbeat row (timestamp + source + counter); it can never touch business tables.

Why an RPC and not a table write? Because the heartbeat table is sealed by RLS (no direct access), and the RPC is SECURITY DEFINER — the ONLY door in. The anon key can bump the heartbeat and do absolutely nothing else.

1.2 Per-project ⚡ and the traffic-light heartbeat

Each row shows the heartbeat age and colours it: fresh ✓ → ⚠ older than the warning threshold (default 3 days) — "ping soon" → 🚨 older than the alarm threshold (default 6 days) — PAUSE RISK. Both thresholds are adjustable in Settings; the alarm is deliberately below Supabase's 7-day line so you always have a buffer.

1.3 Stale-heartbeat wake-up

The moment ANY console page opens, every project not pinged in 5+ days is pinged automatically, silently. Simply opening the console rescues a neglected fleet.

1.4 🤖 Auto-pilot (cross-page)

When enabled (dashboard toggle or Settings), the whole fleet is pinged and health-checked on a timer (default every 12 h) for as long as any console page — including the Wallboard — stays open. The interval is configurable.

1.5 📋 Copyable keep-alive URLs + external cron layers

Every project row has a 📋 button that copies its direct keep-alive URL (RPC + anon key in one line). Feed these to cron-job.org (free, POST, every 3 days) and/or UptimeRobot. The repo also ships a GitHub Actions workflow that pings the entire fleet every 2 days from GitHub's servers using one repository secret. Result: four independent keep-alive layers (console clicks/auto-pilot · cron-job.org · UptimeRobot · GitHub Actions) — any single one alone is enough to prevent a pause.

1.6 ⏸️ Monitoring pause

Retiring a project for a while (school on long break, migration in progress)? Pause it: auto-pilot, fleet-wide actions and alerts skip it, but its registration, notes and history are kept. Resume with one click. This replaces the old dilemma of "delete it or let it spam alerts".

2 · Health monitoring

2.1 🩺 The five-probe health check

  • REST / database API — is PostgREST answering, and how fast (latency in ms)? A 401/404 on the bare root still counts as ALIVE (newer Supabase stacks answer 401 there by design); only network failure or 5xx marks it down.
  • Auth service — GoTrue's health endpoint. If this is down, nobody can sign in even though the site loads: catching it separately points you straight at the culprit.
  • Storage service — the storage status endpoint (uploads/downloads, report attachments, gallery images).
  • Heartbeat age — how long since the last keep-alive write (see §1).
  • Live site — optional site URL fetched in no-cors mode; even an opaque response proves DNS + TLS + a listening server (e.g. Vercel deployment is up).

2.2 Health score (0–100)

Every check computes a transparent, deterministic score: start at 100; −45 if the database API is down, −20 Auth down, −10 site down, −5 Storage down, −10/−25 heartbeat older than warning/alarm threshold, −10 subscription expired, −5 latency > 2.5 s, −5 heartbeat unknown. Bands: 85–100 healthy 60–84 degraded < 60 critical. The weighting mirrors real impact: a dead database dwarfs everything else.

2.3 Latency history, sparklines & uptime %

Each health check stores a sample (latency + up/down + score) — up to 96 per project, kept locally. The dashboard shows a latency sparkline per project; the Reports page turns the same samples into an uptime % and average latency per project plus a fleet-wide roll-up. This is the internal, zero-dependency layer; UptimeRobot remains the external 5-minute-resolution layer.

2.4 Subscription verdict (HMG products)

For School Connect / Tutoring Connect / DramaConnect / HMG CBT projects, the console calls the public sc_license_status RPC and shows the verdict: ✓ active / lifetime, ⚠ grace, or 🔒 expired — data stays alive, renew when ready. This is the fleet-side half of the pause-proof guarantee: an expired client is still kept alive by §1, and you can see at a glance who to follow up with.

3 · Incident journal

3.1 Automatic incidents

Health checks log state transitions automatically, exactly once per transition: API down/up, Auth down/up, site down/up, heartbeat crossed into pause-risk, subscription verdict changed, keep-alive failures, project registered/removed, monitoring paused/resumed. Recoveries auto-mark as resolved. No more "when did that start?" — the journal knows.

3.2 Manual ops diary

Log your own entries per project or fleet-wide with a severity: client called, SQL pack applied, renewal collected, deploy pushed, planned maintenance. Six months later, the searchable history is gold.

3.3 Triage workflow

Filter by project / severity / unresolved-only; resolve or reopen entries; export the journal to CSV; clear resolved entries in bulk. Unresolved critical incidents also surface on the dashboard's "Needs attention" panel.

4 · Business layer (client operations)

4.1 Client contact card

Per project: contact name, phone/WhatsApp, email. When something needs a human (renewal due, site down after their own DNS change), the number is right on the alert — no digging through chats.

4.2 📅 Renewal watch

Set each project's renewal/next-payment date and an optional fee note. The dashboard warns when a renewal is inside the warning window (default 14 days, configurable) and flags overdue ones. The Reports page renders the full renewal calendar, soonest first — your collections worksheet.

4.3 Tags & environments

Free-form tags (lagos, priority, church…) plus an environment badge (production / staging / demo). Both are searchable in every filter box, so "show me every priority school in Lagos" is one keystroke away.

5 · Views & reporting

5.1 📊 Dashboard

KPI strip (projects, healthy, degraded/critical, pause risks), the Needs attention panel (every red flag with its one-click fix button), and the full fleet table with score, keep-alive, health pills, subscription, sparkline and actions. Filter box covers name, tags, type and environment.

5.2 📈 Reports & Uptime

Printable fleet report: SLA table (score, uptime %, average latency, heartbeat age, subscription, last check), renewal calendar and recent incidents. The Print button produces a clean PDF via the browser — monthly ops records or client-facing evidence.

5.3 🖥️ Wallboard (NOC mode)

A full-screen traffic-light grid designed for a spare monitor or TV: green tile healthy, amber degraded, red pulsing critical/pause-risk. It re-checks the entire fleet itself on a configurable interval (default 10 min) — leave it running and the office always knows the fleet state without touching anything.

6 · Ops Toolkit

6.1 🔧 Keep-alive SQL

The one-paste snippet that makes ANY non-HMG Supabase project monitorable: one heartbeat table + one SECURITY DEFINER RPC, nothing else. Idempotent — safe to run twice.

6.2 ⏰ Cron pack generator

Builds, from your live fleet list, (a) the URL list for cron-job.org / UptimeRobot and (b) the exact FLEET_TARGETS value for the GitHub Actions secret. Register a new client → open Toolkit → copy → paste. Done.

6.3 🔍 Anon key inspector

Decodes any Supabase JWT locally: role (a pasted service_role key is flagged in red — and the register form outright refuses one), owning project ref, expiry date. The same validation runs automatically on registration, including a key-vs-URL mismatch check.

6.4 💾 Backup center

One JSON file = projects + settings + incidents + latency history. Old single-file-console backups restore unchanged (same storage key, auto-migrated). A gentle reminder appears if the fleet has no backup in 14+ days. CSV export gives a spreadsheet-friendly fleet overview.

6.5 🧪 Quick probe

Diagnose any Supabase URL + key in seconds without registering it — REST, Auth, Storage, and whether sc_keep_alive exists.

7 · Platform & security model

7.1 Privacy by construction

The console stores ONLY public anon keys. Because every client project enforces Row-Level Security, an anon key can bump the heartbeat, read the public license verdict and… nothing else. The console never signs into a portal, never reads a business table, never requests a service_role key, and rejects one if pasted. Student, fee, result and member data is unreachable by construction, not by promise.

7.2 No server, no tracking

All state lives in this browser's localStorage. There is no backend to hack, no analytics, no third-party script, no CDN dependency — the entire platform is static files that work from Vercel, GitHub Pages, a LAN folder, or file://.

7.3 PWA + offline

A service worker precaches the app shell: the console installs like an app and opens instantly even offline (monitoring calls, of course, need a network). Bump the version constant in sw.js when releasing changes.

7.4 🔐 Optional PIN, 🌓 themes

An optional SHA-256-hashed PIN screen-locks the console once per browser session on shared machines (courtesy lock, not cryptography — §7.1 is the real security). Dark and light themes, persisted.

8 · Known limits (honest engineering)

  • Browser-based checks measure reachability from your network — a client-side ISP issue can look like an outage. Cross-check with UptimeRobot (external vantage point) before declaring one.
  • localStorage is per-browser: use Backup/Restore to move machines, and keep backups because clearing browser data clears the fleet list.
  • Uptime % is sampled (up to 96 samples/project), not continuous — it is a trend indicator; UptimeRobot is the audit-grade record.
  • Auto-pilot needs an open tab; the external cron layers exist precisely to cover closed-tab periods.
